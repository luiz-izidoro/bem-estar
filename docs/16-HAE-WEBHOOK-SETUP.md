# Health Auto Export → Bem Estar Webhook — Step-by-Step

This is the production setup for the iPhone app **Health Auto Export (HAE)**. The application sends Apple Health data directly to Bem Estar over HTTPS; there is no iCloud/Drive JSON hop.

Official HAE references used for this runbook:

- REST API automations: https://help.healthyapps.dev/en/health-auto-export/automations/rest-api/
- Health Metrics JSON format: https://help.healthyapps.dev/en/health-auto-export/export-format/health-metrics/
- Workouts JSON format: https://help.healthyapps.dev/en/health-auto-export/export-format/workouts/

The HAE REST API guide was last updated on 2026-08-23 when this repository was prepared. Re-check it if HAE changes its UI or export schema.

## 1. Prerequisites

Before touching HAE, all of these must work:

```bash
curl -fsS https://bemestar.example.com/healthz
curl -fsS https://bemestar.example.com/readyz
```

Expected JSON includes `"status":"ok"` and `"status":"ready"` respectively.

You also need the **HAE webhook token** from the one-time `ACCESS-CREDENTIALS.txt` generated by:

```bash
python3 scripts/generate_production_config.py --domain bemestar.example.com --username admin
```

The token is different from the Dashboard password, MCP token and Grafana password.

## 2. Common HAE settings

On iPhone:

1. Open **Health Auto Export**.
2. Open the sidebar.
3. Tap **Automations**.
4. Tap **New Automation**.
5. Choose **REST API**.
6. Use the canonical URL:

```text
https://bemestar.example.com/webhooks/hae/v2
```

7. Add HTTP header:

```text
Authorization: Bearer <BEMESTAR_WEBHOOK_TOKEN>
```

8. Add the stream header described for each automation below:

```text
X-Bemestar-Stream: <stream>
```

9. Use **JSON** format.
10. Use **Export Version 2**.
11. Enable **Batch Requests**.
12. For the normal incremental automations, set the date range to **Since Last Sync**.
13. Save the automation.

HAE automatically supplies useful headers such as `automation-name`, `automation-id`, `automation-aggregation`, `automation-period` and `session-id`. Bem Estar stores these as ingestion provenance.

> Do not manually add `Content-Type`; HAE sets it for JSON exports.

## 3. Automation 1 — `bemestar-vitals`

Create a REST API automation named exactly:

```text
bemestar-vitals
```

Custom header:

```text
X-Bemestar-Stream: vitals
```

Data type: **Health Metrics**.

Initial recommended metrics:

- Heart Rate Variability
- Resting Heart Rate
- Heart Rate
- Respiratory Rate
- Blood Oxygen Saturation
- Walking Heart Rate Average
- VO2 Max
- Weight / Body Mass
- Body Fat Percentage
- Lean Body Mass, if available/useful

Recommended export settings:

```text
Format              JSON
Export version      2
Date range          Since Last Sync
Summarize Data      ON
Time grouping       Hours
Batch Requests      ON
```

The goal is to preserve useful trend data without sending all-day heart rate second-by-second.

## 5. Automation 3 — `bemestar-sleep`

Name:

```text
bemestar-sleep
```

Header:

```text
X-Bemestar-Stream: sleep
```

Data type: **Health Metrics**.

Metric:

- Sleep Analysis

Recommended settings:

```text
Format              JSON
Export version      2
Date range          Since Last Sync
Summarize Data      ON
Time grouping       Days
Batch Requests      ON
```

Bem Estar normalizes sleep to the **waking calendar day**. This also protects overnight sessions from being split incorrectly if a later configuration exports sleep stages at finer granularity.

## 6. Automation 4 — `bemestar-workouts`

Name:

```text
bemestar-workouts
```

Header:

```text
X-Bemestar-Stream: workouts
```

Data type: **Workouts**.

Recommended settings:

```text
Format                         JSON
Export version                 2
Date range                     Since Last Sync
Include Workout Metrics        ON
Workout Metrics grouping       Minutes
Include Route Data             OFF
Batch Requests                 ON
```

One-minute workout telemetry is the baseline architecture. It is sufficient for the deterministic training-load features while keeping payload and SQLite growth bounded.

Route/GPS export is deliberately **OFF**. Only enable it if location history is explicitly wanted; it increases privacy sensitivity and storage usage.

## 7. Frequency

HAE exposes scheduling/frequency controls. A conservative initial setup is:

| Automation | Suggested cadence |
|---|---:|
| vitals | hourly |
| activity | every 1–2 hours |
| sleep | morning + a later daily retry, or the closest cadence HAE allows |
| workouts | hourly |

This is not a real-time medical telemetry system. iOS does not let apps freely access Health data while the device is locked, and background execution is opportunistic. The system therefore uses idempotent reconciliation rather than assuming every scheduled run will fire exactly on time.

## 8. Test each automation

Before enabling broad history:

```bash
sudo journalctl -u bem-estar-rest.service -f
```

Then trigger the automation manually from HAE.

Expected behavior:

1. HAE receives HTTP `202`.
2. REST logs show the request.
3. Dashboard → **Data** shows a new ingestion.
4. The worker changes it from `pending` → `processing` → `processed`.
5. `records_inserted`, `records_updated`, and `records_ignored` make sense.

Server-side inspection:

```bash
sudo journalctl -u bem-estar-worker.service -n 100 --no-pager
curl -fsS https://bemestar.example.com/readyz
```

## 9. Reconciliation

Apple Health data can arrive late or be revised. Bem Estar's canonical identity is specifically designed so a resent logical sample is ignored when unchanged and **updated in-place when corrected**, rather than duplicated.

After the normal sync has been stable for a few days, add reconciliation runs using **Last 7 Days**. Use:

```text
X-Bemestar-Stream: reconciliation
```

A practical minimum is one Health Metrics reconciliation and one Workouts reconciliation. Reusing the same metric selections as the main automations is safest.

## 10. Historical bootstrap

Do not attempt the complete Apple Health history in one enormous request.

Use HAE's manual/historical export with:

```text
X-Bemestar-Stream: history
Batch Requests: ON
```

Start with ~30-day windows. Check HAE activity logs and server processing times, then increase the window only if both sides remain healthy.

The backend stores the original request body compressed in the RAW inbox, then normalizes it asynchronously. The HTTP webhook itself returns quickly.

## 11. Troubleshooting map

### HAE shows 401

The `Authorization` value is wrong. It must be:

```text
Bearer <BEMESTAR_WEBHOOK_TOKEN>
```

Do not use the MCP token.

### HAE shows 413

Payload exceeded the 25 MB edge/backend limit. Ensure **Batch Requests = ON**, reduce selected metrics, increase time grouping, or use a smaller historical window.

### HAE shows 507

The server has fallen below its configured free-space safety floor (default 1 GiB). Free space before retrying.

### HAE shows 5xx/timeout

Check:

```bash
sudo journalctl -u bem-estar-rest -n 100 --no-pager
sudo journalctl -u bem-estar-worker -n 100 --no-pager
sudo systemctl status bem-estar-rest bem-estar-worker
```

### HAE runs are delayed

Check the HAE Activity Log first. iOS health/background restrictions are expected. Keep reconciliation enabled rather than trying to make this architecture pretend the phone is an always-on server.
